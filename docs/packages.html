Các package trong radard

radard là một monorepo Bun. Thư mục packages/ chứa ba thư viện nội bộ mà app daemon dùng: @radard/core @radard/adapters @radard/db. Trang này giải thích từng package có gì, vì sao chia như vậy, và chúng phối hợp ra sao trong một lượt cào tin.

Tóm tắt
  • core là các hợp đồng (interface) và tiện ích thuần: nguồn là gì, kho bản thô là gì, cách băm, cách chuẩn hoá URL, cách gọi HTTP lịch sự. Không phụ thuộc package nào.
  • adapters là cài đặt cụ thể của các interface đó cho một nhà cung cấp; hiện có kho bản thô ghi ra đĩa, sau này có R2, Telegram…
  • db là schema database, kết nối và migration; nơi duy nhất biết cấu trúc bảng.
  • apps/daemon ghép ba thứ trên thành chương trình chạy thật: adapter nguồn, job fetch, scheduler, worker, CLI.

2.1 SourceAdapter: hợp đồng của một nguồn

packages/core/src/source.ts
export interface RawItem {
  externalId: string;    // id phía nguồn; cùng source_id là khoá chống trùng
  url: string;
  title?: string;
  publishedAt?: Date;
  body: string;          // nội dung gốc đúng như nhận được (JSON, HTML, XML)
  contentType: string;
  meta?: Record<string, unknown>;   // vài trường tiện tra: điểm, tác giả…
}

export interface FetchContext<C, S> { config: C; state: S | undefined; http: HttpClient; now: Date; }
export interface FetchResult<S>     { items: RawItem[]; state: S; notModified?: boolean; httpStatus?: number; }

export interface SourceAdapter<C = unknown, S = unknown> {
  readonly kind: string;                           // "hn", "arxiv"… khớp cột sources.kind
  fetch(ctx: FetchContext<C, S>): Promise<FetchResult<S>>;
}
Vì sao state là “hộp đen”?

Mỗi nguồn cần một kiểu con trỏ khác nhau: HN nhớ lastCreatedAt, GitHub sẽ nhớ ETag từng repo, RSS nhớ Last-Modified. Lõi chỉ cất và trả lại nguyên vẹn (cột jsonb), nên thêm nguồn mới không phải đổi schema.

Vì sao giữ body nguyên văn?

Bản thô là nền của nguyên tắc “không bao giờ sửa”: khi lớp 2 đổi cách trích xuất, radard đọc lại bản thô thay vì cào lại nguồn.

2.2 ObjectStore và rawKey()

packages/core/src/object-store.ts
export interface ObjectStore {
  put(key: string, body: Uint8Array<ArrayBuffer>, contentType: string): Promise<void>;
  get(key: string): Promise<Uint8Array<ArrayBuffer> | null>;
  exists(key: string): Promise<boolean>;
}
export function rawKey(sha256: string): string {
  return `raw/${sha256.slice(0, 2)}/${sha256}.gz`;   // raw/61/61d453ef…2841.gz
}
  • Key theo hash nội dung (content-addressed): cùng nội dung thì cùng key, ghi lại là vô hại; hai nguồn trả về cùng thứ chỉ tốn một chỗ.
  • Tách thư mục theo 2 ký tự đầu: 256 thư mục con, để một thư mục không chứa hàng trăm nghìn file (chậm với hệ thống file). Hiện 737 file nằm trong 241 thư mục.
  • Kiểu Uint8Array<ArrayBuffer> chứ không phải Uint8Array thường: Bun.gzipSync chỉ nhận mảng gắn với ArrayBuffer (không phải SharedArrayBuffer). Thu hẹp kiểu ở interface thì không phải sao chép dữ liệu.

2.3 hash.ts: băm sau khi chuẩn hoá NFC

export function sha256(input: string | Uint8Array): string {
  const hasher = new Bun.CryptoHasher("sha256");
  hasher.update(typeof input === "string" ? nfc(input) : input);
  return hasher.digest("hex");
}

“ệ” có thể lưu là 1 ký tự (U+1EC7, NFC) hoặc 3 ký tự (e + dấu nặng + dấu mũ, NFD). Không chuẩn hoá thì cùng nội dung ra hai hash khác nhau và dedup hỏng. Chuỗi được chuẩn hoá ở đây; job fetch chuẩn hoá body trước khi mã hoá thành byte, nên cả hai đường đều ra NFC. Chi tiết trong lab-notebook: 2026-09-28-nfc-nfd-tieng-viet.

2.4 url.ts: khoá so sánh URL

2.5 http.ts: gọi HTTP lịch sự

packages/core/src/http.ts (rút gọn)
export function createHttpClient(opts: { minIntervalMs?: number } = {}): HttpClient {
  const minInterval = opts.minIntervalMs ?? 1000;
  const nextAllowed = new Map<string, number>();         // host → thời điểm sớm nhất được gọi tiếp

  async function waitTurn(host: string) {
    const now = Date.now();
    const at = Math.max(now, nextAllowed.get(host) ?? 0);  // lượt của mình
    nextAllowed.set(host, at + minInterval);             // giữ chỗ cho người sau
    if (at > now) await Bun.sleep(at - now);
  }

  return { async get(url, o = {}) {
    await waitTurn(new URL(url).host);
    if (o.etag) headers["if-none-match"] = o.etag;             // GET có điều kiện
    if (o.lastModified) headers["if-modified-since"] = o.lastModified;
    const res = await fetch(url, { headers, signal: AbortSignal.timeout(o.timeoutMs ?? 30_000) });
    const body = res.status === 304 ? "" : await res.text();   // 304: không tải lại body
    if (res.status >= 400) throw new HttpError(res.status, url, body.slice(0, 300));
    …
  } };
}
GET có điều kiện

Gửi kèm ETag hoặc Last-Modified của lần trước. Nội dung chưa đổi thì server trả 304 không kèm body: tiết kiệm băng thông, và với GitHub một request 304 có kèm token (header Authorization) không bị trừ quota; không có token thì vẫn bị trừ. HN chưa dùng (API Algolia không trả ETag); GitHub và RSS ở tuần 2 sẽ dùng.

Giãn request theo host

Mỗi host có một “vé” thời gian. Ba request tới cùng host gửi cùng lúc sẽ tự xếp hàng ở 0 giây, 1 giây, 2 giây; request tới host khác không bị ảnh hưởng. Cách này “giữ chỗ” trước khi ngủ nên đúng cả khi nhiều job chạy song song.

Thêm: timeout 30 giây để một nguồn treo không giữ worker mãi; User-Agent ghi rõ radard kèm link liên hệ, là phép lịch sự khi cào; lỗi 4xx/5xx thành HttpError có mã và đoạn đầu body, để fetch_runs.error đọc được nguyên nhân.

2.6 log.ts

Một dòng mỗi sự kiện dạng thời-gian phạm-vi thông-điệp khoá=giá-trị, ví dụ 2026-09-28T00:15:23Z worker fetch xong sourceId=1 nNew=2. Không dùng thư viện log vì dữ liệu cần truy vấn đã nằm trong bảng (fetch_runs); log chỉ để đọc bằng mắt trên terminal và Railway.

3. @radard/adapters: cài đặt cụ thể

Nơi duy nhất được import SDK hay API riêng của một nhà cung cấp. Hiện có một adapter:

packages/adapters/src/object-store-fs.ts
export function fsObjectStore(root: string): ObjectStore {
  const pathOf = (key: string) => join(root, key);
  return {
    async put(key, body) {
      await mkdir(dirname(pathOf(key)), { recursive: true });
      await Bun.write(pathOf(key), Bun.gzipSync(body));      // nén trước khi ghi
    },
    async get(key) {
      const file = Bun.file(pathOf(key));
      if (!(await file.exists())) return null;
      return Bun.gunzipSync(new Uint8Array(await file.arrayBuffer()));
    },
    exists: (key) => Bun.file(pathOf(key)).exists(),
  };
}
  • Khi dev ghi vào ./data (biến DATA_DIR); test ghi vào thư mục tạm rồi xoá.
  • Nén nằm ở adapter, không ở lõi: R2 có thể muốn nén kiểu khác hoặc để Cloudflare tự nén. Key đã có đuôi .gz nên hai adapter đọc được bản của nhau.
  • Tuần 3 thêm object-store-r2.ts (qua Bun.s3) và notifier-telegram.ts ngay cạnh file này; job fetch không đổi dòng nào.

Vì sao adapter nguồn HN nằm ở apps/daemon/src/sources/ chứ không ở đây? Adapter nguồn gắn với việc cào của daemon và có danh bạ theo sources.kind; còn packages/adapters dành cho hạ tầng mà nhiều app dùng chung (kho bản thô, kênh thông báo). Ranh giới này có thể xem lại khi có app thứ hai.

4.2 Kết nối: client.ts

export function createDatabase(url?: string, opts?: { max?: number }) {
  const client = new SQL(url ?? databaseUrl(), opts ?? {});   // SQL client có sẵn của Bun
  const database = drizzle({ client, schema });
  return Object.assign(database, { $bun: client });           // giữ client gốc để .close()
}

Dùng driver bun-sql của Drizzle: không kéo thêm pg hay postgres.js cho phần code của radard (pg-boss vẫn dùng pg riêng của nó). $bun để CLI và test đóng kết nối khi xong, nếu không tiến trình treo. Test đặt max: 2 để nhiều file test không vượt giới hạn kết nối của Postgres.

4.3 Migration: migrate.ts

await client`select pg_advisory_lock(${LOCK_KEY})`;       // chỉ một tiến trình được migrate
try {
  await database.execute(sql`create extension if not exists vector`);
  await database.execute(sql`create extension if not exists pg_trgm`);
  await migrate(database, { migrationsFolder: MIGRATIONS_FOLDER });
} finally {
  await client`select pg_advisory_unlock(${LOCK_KEY})`;
}
Khoá tư vấn (advisory lock)

Trên Railway nhiều service cùng image khởi động cùng lúc và đều chạy migrate. Hai tiến trình cùng CREATE TABLE thì một cái chết. Khoá tư vấn của Postgres cho đúng một tiến trình làm, các tiến trình khác chờ rồi thấy đã xong.

Bật extension sẵn

vector (pgvector) và pg_trgm chưa dùng ở lớp 1, nhưng bật từ đầu để migration lớp 2 ở tuần 2 không hỏng trên máy hay server chưa bật.

Quy trình khi đổi schema: sửa file trong src/schema/ → bun run db:generate sinh file SQL mới → xem lại SQL → bun run cli db migrate (daemon cũng tự migrate khi khởi động).

5. Một lượt cào đi qua các package

Hàm runFetch() ở apps/daemon/src/jobs/fetch.ts là nơi ba package gặp nhau:

Đọc nguồn và trạng thái db

sources id=1 (kind hn, config {backfillHours: 24}) và source_state.state = {lastCreatedAt: 1790553374}. Ghi một dòng fetch_runs trạng thái running.

Gọi adapter nguồn daemon core

hnSource.fetch() gọi API Algolia qua HttpClient (giãn theo host, timeout 30 giây), trả về RawItem[] và state mới.

Lọc mục đã có db

Một câu SELECT lấy các external_id đã tồn tại, để không nén và ghi lại bản thô của chúng.

Lưu bản thô core adapters

Với mỗi mục mới: chuẩn hoá NFC → sha256() → rawKey() → store.put() (hiện là fsObjectStore, nén gzip).

Ghi tài liệu db core

INSERT … ON CONFLICT DO NOTHING vào documents với url_canonical = canonicalizeUrl(url). Bản trùng (do khoảng lùi 60 giây) tự bị bỏ.

Chốt lượt db

Thành công: lưu state mới, fail_count = 0, fetch_runs → ok với số lấy/mới. Lỗi: fetch_runs → error, fail_count + 1, state giữ nguyên, rồi ném lỗi lại để pg-boss retry.
